## Why

A reviewer opening a report wants to know what was asked, what changed, what was verified, what is still unverified and what needs their judgment. The report had most of the facts, but in the order the checker produced them (contract line, claims, an obligation table, cost, limitations), and it never recorded some of them: which files the task changed, which acceptance tests passed one by one, and which changed modules any test imported. In the T93 to T95 trial a simulated user reported review time going from 8 to 6 minutes with the report and another from 10 to 7. Those are simulated users, not measurements.

- The module-load plugin from T90c (`ohx_where`), now also read for which project modules each pytest run imported.
- Mutation results (T87 item 5) and approvals (T90b, T90e).

## Added

- `report/brief.py` (pure, no I/O): five sections at the top of every report, then `## Details` with the report as before.
  1. **Requested outcome**: contract title, mode, summary, revision and who accepted it. Says it is checked only through the acceptance tests, or that none were agreed.
  2. **What changed**: files that differ by content digest from the files accepted with the contract, each marked added, modified or deleted, a kind (code, test, configuration, dependencies, docs, other) and, for Python code, whether any test run imported it. Labelled as observed; says that why each file changed is not recorded and that an agent's own account is not evidence. A diff command (or, on GitHub Actions, a compare link).
  3. **What was verified**: only checks with status pass, mandatory first, each with a link to its recorded output. Acceptance checks list the agreed tests that passed. Ends with the caveat that a passing check does not show every changed line ran, nor that a requirement with a passing test is fully tested. In a stale report it opens by saying the results are for an earlier state and names the files changed since.
  4. **What remains unverified**: every check that did not pass (mandatory first) with its note and output link; agreed tests that failed; no acceptance tests; no regression check; tests failing or skipped both before and after; changed Python files no acceptance test imported (no test run, without acceptance); non-Python code whose test coverage is not recorded; unsandboxed checks; limitations.
  5. **Decisions for you**: numbered questions from rules over the records: verify again (stale), do not rely on it (integrity), send back or revise the contract (a failed mandatory check; a report cannot waive it), is the outcome done (no acceptance), do these lines need a test (mutation survivors), review by hand (changed code no acceptance test imported), are the changed tests right, configuration changed, dependencies changed, tests still failing as before, checks ran without the sandbox. With none: "None found in the records. This brief does not replace reading the diff."
- `verify` records `changes`, `acceptance_tests`, `imported`, `obligation_kinds` and `evidence` (for each check: `evidence/<id>.txt`, the output blob digest and the observation record), and writes the output copies next to `report.md`. The limitation "0 ignored file(s) present" is no longer listed when there are none.
- `ohx gate` copies `evidence/` into its output folder, compares against the pull request's base commit and adds a compare link on GitHub Actions.
- A report recorded by an earlier version renders, and says each missing part was "not recorded by the OpenHarnX version that made this report".

No model calls. Readiness, exit codes, READY and NO REGRESSIONS are unchanged; the brief only reads them.

## Validation

- `tests/test_review_brief.py`, 12 tests: the five sections in order; every verification claim links to an output file that exists; NO REGRESSIONS asks whether the outcome is done and claims no acceptance; a failed and an unavailable mandatory check appear only under unverified; changed code no acceptance test imported is named; missing per-test results and missing import records are said plainly; a stale report says so in the verified section and asks to verify again; test, configuration and dependency changes are put to the reviewer; a report from an earlier version renders; the gate's brief lists the pull request's files and its evidence links resolve; no model calls and "authorizes nothing" kept.
- `./scripts/check.sh`: 515 passed, 14 skipped (macOS).
- `ohx verify --sandbox srt` with the installed `d9b6872`: READY, 642 s (the mutation check took 504 s: ten mutants, each running the 50-second acceptance file).

## Limitations

- "Imported" means a pytest run loaded the module, not that the changed lines ran. JavaScript, TypeScript and Go runs do not record it, and the brief says so.
- Per-test acceptance results need JUnit output: pytest always, other runners only when their command uses `{junit}`. Without it the brief says the evidence is for the check as a whole.
- "What changed" compares with the files accepted with the contract. Re-accepting a contract after editing resets it, as this repository's own dogfood loop does when a test changes.
- File kinds come from file-name rules and can be wrong for unusual layouts.
- Decisions come from fixed rules over the records. They can miss what the records do not hold (a wrong algorithm the tests do not exercise, a design problem), and the brief says it does not replace reading the diff.
- In the GitHub job summary the output links are relative to the uploaded artifact, so they do not open there; the artifact holds them.
- Each check's output is written twice locally (blob and copy).
- Nothing here is measured with real reviewers.

## Follow-ups assessed (not built)

| Extension | What exists | Observed friction | Size |
|---|---|---|---|
| Requirement tracing in the brief | `ohx trace` (units to tests), separate from the contract | None observed: no trial user and no replay used it | Medium: tie the trace file to the contract, show units without evidence |
| Changes since the last reviewed revision | Stale detection, `ohx history` | None observed yet: every trial task was one round | Medium: needs a "reviewed" record, then a diff of two reports |
| Feedback to the current agent | Stop hook sends BLOCKED back with the report | u1 and u3: the hook's verdict was invisible in `claude -p`, and the report said "Agent work: unknown" | Small: send the brief's unverified and decision sections, and say NO REGRESSIONS and READY to the agent too |
| Mutation and test-quality findings | Mutation check, weakening, tests failed or skipped both times | Partly surfaced now (survivors are a decision) | Small, mostly done by T96 |

**Recommendation:** improve feedback to the current agent next. It is the only one of the four with observed friction (two of four trial users), it shortens repair rounds directly (a blocked agent sees the same unverified list the reviewer will), and it reuses the brief without new records. Revisit tracing and "since last reviewed" when a pilot shows multi-round reviews or requirement documents in use.

## Proposed pilot (not run)

Target: a 25% reduction in median active review time per change, as an experiment, not a claim.

- **Who and what:** 4 to 6 engineers who already review coding-agent changes, on their own repositories; 10 or more agent changes each, alternating with and without the brief (same person, comparable tasks, order randomised).
- **Measures:** active review time (screen time on the change, from a timer the reviewer starts and stops, idle time excluded); repair rounds to merge; setup minutes for OpenHarnX; OpenHarnX overhead per change (verify wall time, which the report records); findings in the brief the reviewer judged unnecessary; defects found after merge (2-week window) and defects the brief missed; whether the reviewer's decision changed.
- **Reporting:** medians with ranges and all raw rows; overhead counted against savings; quality outcomes reported next to any time saving; no claim from fewer than 20 changes per arm.
