## Item 1: a candidate file replaced the checker (VERIFY-11)

**Cause.** Checks run as `{python} -m <module>` with the candidate as working directory. Python puts that directory first on `sys.path`, so a `pytest.py`, a `pytest/` package or a module pytest imports (such as `pluggy.py`) in the candidate ran instead of the real one. The sandbox does not help: the fake is a legitimate read of the candidate.

**Reproduction first.** `tests/test_checker_shadowing.py`, locked in contract 0007. Against the code at `fb39881` all five attack cases returned READY, including the one under real srt; the four controls passed.

**Fix.** `openharnx.verify.guard_module_run` rewrites `{python} -m <module> args` to `{python} -P -c <launcher> <module> args`. The launcher requires the module to resolve before the candidate is on `sys.path` (otherwise exit 120, which is not a pass), then appends the candidate last and runs the module with `runpy`. Project code stays importable by the locked tests; the candidate cannot replace the checker or anything it imports from the interpreter's own paths.

**Results.**
- `OHX_SRT=$(which srt) uv run pytest tests/test_checker_shadowing.py`: 9 passed (includes the srt case).
- `./scripts/check.sh`: all checks passed.
- `ohx verify --sandbox srt` (frozen verifier): READY; candidate digest in the commit message.

**Contract revision.** The acceptance test was revised once after acceptance: one line exceeded the lint limit. Behavior unchanged; re-accepted as a new contract revision.

**Process note.** The drafted tests for T78 (`tests/test_progress.py`) and trace in the gate (`tests/test_trace_gate.py`) target unbuilt features and fail the checks, so they were kept out of the candidate while verifying and restored afterwards, still uncommitted.

**Limits.** See threat model T17 residual: `conftest.py`, plugins and `addopts` still run inside pytest (item 9, owner proposal 2); optional imports installed nowhere; console-script checkers are not rewritten. The frozen verifier that judged this change predates the fix.

## Item 2: concurrent appends broke the hash chain (STATE-13)

**Cause.** `Store.append` read the idempotency key and the chain head before its write transaction began (Python's sqlite3 opens the transaction only at the first insert). Two writers could read the same head and both link to it; two writers with the same idempotency key could both pass the check.

**Reproduction first.** `tests/test_store_concurrency.py`, locked in contract 0008: 8 processes, 150 appends each, started together. Against `4203c02` the chain broke in 22 and then 33 places on two runs, and the same-key case failed.

**Fix.** The connection runs in autocommit mode with a 60 second busy timeout, and `append` opens `BEGIN IMMEDIATE` before reading the idempotency key and the chain head, then commits, or rolls back on any error. Writers now serialize on SQLite's write lock.

**Results.**
- `uv run pytest tests/test_store_concurrency.py`: 3 passed on three consecutive runs.
- `./scripts/check.sh`: all checks passed (75 passed, 3 skipped).
- `ohx verify --sandbox srt` (frozen verifier at `4203c02`): READY; candidate digest in the commit message.

**Limits.** Tested with 8 local processes on one machine and APFS; not tested on network file systems, where SQLite locking is unreliable. A writer that waits longer than 60 seconds fails with an error, which is not recorded as evidence. The review's original scale (12 writers, 3,600 events) was not rerun.
