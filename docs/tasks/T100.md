## Why

An external launch review (2026-10-06) found enough functionality for an early release and listed what blocked it: `main` unprotected, outside contributors' workflows approved only the first time, no release, version 0.0.1, CI last run on 2026-10-03 (before T96 to T99), CI signing never exercised, a README whose scope went past the release boundary, and one demo test that failed on the reviewer's machine. It asked that the exact release candidate go through CI before any tag.

## What running the candidate through CI found

The first two CI runs failed. Each failure was a real defect that local verification on macOS had not shown; each is fixed with tests and was verified READY under srt before it went in.

| Defect | Found in | Fix |
|---|---|---|
| Bumping the project's own version changes its line in `uv.lock`; the gate read that as a changed environment and made every check invalid, so every version bump in a uv project would be UNKNOWN | run 37466222249 | `b99825d` (contract 0060): only the version line of the package whose source is the project itself is set aside |
| On Ubuntu's Python 3.12.3 the T99 interpreter fingerprint covered only the standard library: Debian patches sysconfig's default scheme, so asked without site setup, a venv's packages were looked for in a folder that does not exist. A planted `.pth` went unnoticed there while the report said later changes are caught; T99's tests did not check which folders were covered | run 37467770319 | `8d47009` (contract 0061): the `venv` scheme, the usual venv layout and `site.getsitepackages()`; the report names the folders; tests simulate Debian's scheme on macOS |
| The locked copy of the suite ran with a fixed 300-second limit and timed out (the same suite took 566 s in parallel under srt on the runner) | run 37467770319 | `8d47009`: `suite_timeout_s` in `ohx.toml` for every suite OpenHarnX adds; OpenHarnX's own suite runs in parallel with 1200 s, the job may take 60 minutes |
| `ohx approve-tests` stores a git note, and git refuses without a committer identity; the runner has none, so seven signed-approval tests had failed in CI since T90e, unseen because CI did not run | run 37473579890 | `ce3e772` (contract 0062): without a usable identity the note is written as "OpenHarnX approval"; a configured identity is kept |

`b99825d` and `8d47009` were pushed to `main` directly with the owner's approval: in CI the gate judges a pull request with the base branch's verifier and configuration, which these two commits fix, so a pull request carrying them could not pass under the base that judged it. `ce3e772` and the release candidate went through CI together in pull request #4.

## Release steps

1. Outside contributors' workflow runs now always need approval (`all_external_contributors`), as decided on 2026-10-03.
2. Release candidate (`0162666`): version 0.1.0; the README opens with a first run (install pinned with the sandbox, the cheat demo, protect a project, change it, read the brief) and separates what 0.1.0 supports (Python with pytest, macOS locally, Linux in CI, srt) from what is experimental; `.github/CODEOWNERS`; the demo cleanup test allows known operating-system caches (the reviewer's failure was macOS's `xcrun_db` cache in TMPDIR; it did not reproduce here, so this is a robustness fix, not one seen to fail first).
3. CI run 37478954436 on `0162666`: NO REGRESSIONS, every check passed under srt (locked suite 530 s, the pull request's own 529 s). `gh attestation verify report.json -R rupeshpoojary9/OpenHarnX` verified the report's digest (`3445acfd...`), signed by `.github/workflows/gate.yml` in that run (RC-24).
4. `main` fast-forwarded to `0162666` (same SHAs; pull request #4 closed as merged). Branch protection: the `gate` check required, code-owner review required, force pushes and deletion refused, admins exempt (RC-17). The protection was confirmed through the API, not by attempting a force push.
5. Signed tag `v0.1.0` with the owner's SSH key, verified by GitHub; GitHub release with notes naming the commit, the CI run and how to verify the attestation.
6. From the public URL in a fresh environment: `uv tool install git+https://github.com/rupeshpoojary9/OpenHarnX@v0.1.0` gave `ohx 0.1.0`, `ohx doctor` passed, and the cheat demo from a public clone at the tag passed (RC-25). Protecting a project and verifying a change (quick start steps 3 and 4) were run from a fresh install of the equivalent candidate `d5b8040`: NO REGRESSIONS with srt enforced.

## Limitations

- An admin can push to `main` past the required check and the review; the owner is the only admin.
- A pull request that edits the workflow still runs its own version of it; the required review stops the merge, not the run (threat model G10, now mitigated rather than prevented).
- CI under srt is slow: about 9 minutes per full suite run on a 4-core runner, three runs per pull request.
- Nothing here measures review time or production safety; the release notes say so.

## Lesson

CI on the target platform belongs in every release, not only the first: it did not run between 2026-10-03 and 2026-10-06 while T89 to T99 landed, and three of the four defects above had been sitting there unseen.
