## Why

The owner's full `ohx bug` run on a practice copy of another repository (READY in one attempt) and a gap review against the threat model found five gaps, in order of harm:

1. The project's own test suite was advisory, so an agent that broke other tests still got READY.
2. `ohx bug approve` locks the proposed tests as the oracle, but the owner saw only the rule.
3. No record of who did what: no identities, and no list of the files each agent run changed.
4. Evidence is not signed, so it cannot be checked away from the machine that made it (threat T7).
5. A proposed test counts as reproducing the bug however it fails.

## Item 1: regression baseline (done)

- At acceptance, each advisory regression suite runs once and its per-test results are recorded in the contract (`regression_baseline`). pytest writes them as JUnit XML, requested through `PYTEST_ADDOPTS`, so the checker command stays as written.
- A mandatory built-in check, `no-new-failures`, compares at each verification: a test that passed at acceptance and fails, is skipped or no longer runs blocks, and so does a new test that fails. Failures that were already there are named in the report and do not block.
- Without per-test results the whole suite is compared; a suite already failing at acceptance gives unknown, never a pass.
- Mandatory suites get no baseline: every failure already blocks.
- `ohx contract new|accept --sandbox` chooses where the baseline runs; `ohx bug approve` uses the sandbox of the investigation.
- Evidence: `tests/test_regression_baseline.py` (contract 0015). Against `f797d6d` the fixture's agent-style change that breaks `test_mul` was READY.

Limits: a baseline taken at acceptance trusts the tree at acceptance; re-accepting a contract mid-change re-takes it (as for the weakening check). A test inside the suite could overwrite the JUnit file during the run; the weakening check blocks new conftest or plugin code, not test bodies. Acceptance takes as long as one suite run.

## Item 2: show the tests at approval (done), with part of item 5

- The reproduction run records each proposed test's result and failure reason (JUnit XML through `PYTEST_ADDOPTS`).
- `ohx bug new` lists every proposed test before the approve step: `fails on the current code (AssertionError)`, or flagged: `passes on the current code, so it does not show the bug`, or `fails with NameError, not a failed assertion; check that it tests the rule`. Parametrized cases are counted.
- `ohx bug show BUG-001` prints the proposal and the full test file. The approve prompt now reads "If the rule and the tests are right".
- Evidence: `tests/test_approval_shows_tests.py` (contract 0017).

Limits: flags are shown, not enforced; the owner decides. Whether the tests catch plausible wrong fixes (mutation checks) is the rest of item 5.

## Item 3: audit trail (done)

- Each agent run records the agent's identity (adapter, the command started, and the model, version and session the agent reports; for Claude Code from its stream's init event) and the files it changed, observed from snapshots taken before and after the run. A shell `sed -i` that the agent never reports as an edit is attributed the same way. Both snapshots are kept.
- Contract acceptance records who accepted (git `user.name` and `user.email`), the contract file and acceptance tests it brought in, and a snapshot of the tree. `ohx bug approve` records who approved.
- `ohx audit` prints the trail, one line per event: reported, investigated, approved, accepted, each agent run with what it changed, verification and verdict. A difference between two recorded states that no recorded actor accounts for is shown as "changed outside OpenHarnX (no recorded actor)", so work by another agent or a person still appears, with its author unknown.
- Records from before this change read "unknown"; nothing is inferred.
- Evidence: `tests/test_audit_trail.py` (contract 0018). Seen on the owner's practice store: the trail reads correctly with the older records.

Limits: identities are as declared (git configuration, the agent's own report) and can be set by anyone with access to the machine; signed evidence (item 4) is what makes them checkable. OpenHarnX runs one agent at a time; several agents working at once are attributed per run only when OpenHarnX launches them, and otherwise appear as changes outside OpenHarnX. Reads and network use are not recorded.

## Item 4: signed evidence (done, local)

Owner decision 2026-10-03: sign locally with the owner's own SSH key; sign in CI as the pipeline (Sigstore keyless) in T79.

- Each command that writes evidence (`init`, `contract`, `verify`, `bug`, `trace`) ends by signing the head of the hash chain with `ssh-keygen -Y sign`, namespace `openharnx`. Every record is chained into the head, so one signature covers everything before it. The signature is a record of its own, with the public key, its fingerprint and the git user.
- The key: `OHX_SIGNING_KEY` (a public or private key file; `none` turns signing off), else git's SSH signing key, else `~/.ssh/id_ed25519`, `id_ecdsa`, `id_rsa`. Signing never fails a command; when it cannot sign it says so on stderr.
- `ohx store check` verifies every signature against the chain as it is now, names each signer with the record it signed through, and counts unsigned records at the end. `--signer <public key file or SHA256 fingerprint>` pins the expected key. `ohx report` shows whether the report is signed and by whom; a signature that no longer matches makes it invalid. `ohx audit` shows each signature.
- The test suite sets `OHX_SIGNING_KEY=none` (new `tests/conftest.py`, accepted with this contract) so tests never sign with the developer's key; the signing tests generate throwaway keys.
- Evidence: `tests/test_signing.py` (contract 0019). Against `cf17fbe`, a chain rewritten and re-hashed by an attacker passed `ohx store check`.

Limits: a signature proves the records came from the holder of the key, not that the machine was clean when they were made. An unencrypted key file can be copied and used by anyone who can read it; a key held in ssh-agent or with a passphrase is better. Checking the key against the owner's GitHub keys is a manual step for now (`https://github.com/<user>.keys`). Records written by another command at the same moment may sit between two signatures until the next command signs. Requires OpenSSH 8.2 or later.

## Item 5: mutation checks (done)

Owner default 2026-10-03: advisory. Mutation testing has equivalent mutants (a change that does not alter behavior survives any test), so a survivor is a question for the reviewer, not proof of a weak test.

- Contracts with acceptance tests get a built-in, advisory `mutation` check at acceptance; `ohx bug approve` contracts too. It never changes the verdict.
- At verification, after every acceptance test passed, OpenHarnX finds the lines of source files (Python, not tests) that differ from the base commit, makes up to 10 mutants of those lines (a comparison or arithmetic operator swapped, `and` for `or`, a number moved by one, a boolean flipped), spread one per line first, and runs the acceptance tests against each in a copy of the tree. Unchanged lines are never mutated, so a survivor points at the change.
- The report names each survivor, as in the weak-test case: "2 of 3 mutants of changed lines survived: calc.py:6 `part * 100 / whole` -> `part * 100 * whole`; calc.py:6 `100` -> `101`". All killed is a pass; no changed source lines, or acceptance tests that did not pass, is unavailable, never a pass.
- Found while designing it: a protected checker environment makes the repository importable through a `.pth` file, so a mutated copy elsewhere would be ignored and every mutant would wrongly survive. The copy lives at one fixed place in the store with its own protected environment, and each mutant ends with a probe that marks when the module is imported; a mutant the tests never imported is "not exercised", never a survivor or a kill.
- A changed lockfile stops this check like every other (found by `tests/test_protected_environment.py`).
- Evidence: `tests/test_mutation.py` (contract 0028): a weak test (`percent(1, 1) > 10`) lets 2 of 3 mutants of the fix survive while the verdict stays READY; a strong one kills 3 of 3; only the changed line is mutated; docs-only changes are unavailable; failing acceptance tests are not mutated; the repository is untouched; mutants are imported from the copy with a protected environment; the same under srt.

Limits: Python only. Without a protected environment (`environment = "uv"`), a project installed in editable mode imports from the repository, so its mutants are not exercised and the check says so. The changed lines are those against the base commit, so uncommitted work from before acceptance counts too. Each mutant costs one run of the acceptance tests.
